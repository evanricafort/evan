Reading the verdict

CONSISTENT — the write-up, the steps and the capture describe the same test on the same targets.
CONTENT MISMATCH — the finding stands, but something it states contradicts its own capture.
INSUFFICIENT EVIDENCE — the capture does not cover the hosts, ports or window the finding claims.
POSSIBLE FALSE POSITIVE — not substantiated as written: the command shown could not produce that output, or a host other than the target answered.

Each issue is tagged model or checker — written by Gemini, or by the deterministic pass. A model issue must quote your finding verbatim; quotes that are not literally present are discarded before the verify pass runs, and the header reports how many were dropped.

A verdict is a document review, not a re-test. POSSIBLE FALSE POSITIVE means the report does not prove the finding as written — not that the condition is absent.

Before you deliver

1. Re-run the corrected command and paste your real capture over the PoC. A drafted expected-output block is a target to aim for, never evidence.
2. Fill every <angle-bracket placeholder> the rewrite left behind — they are deliberate blanks, not finished text.
3. Read the generalised fields once: <Affected Target> should fit the sentence it landed in.
4. Check the Affected list is still the scope you validated. Nothing is ever removed from it, but coverage notes tell you which hosts carry no transcript.
5. Scrub anything the capture leaked — local paths, other engagements’ filenames, unrelated hostnames.

Nothing is stored server-side. The finding text goes to Google’s API on each run; the key stays in this browser.
